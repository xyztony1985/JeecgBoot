# PRD Review — 独立质检

让一个干净旁观者、没有"面子"包袱的角色来审，比让写 PRD 的人自己回头看，挑出的问题更狠、更准。

## 边界 / 不适用场景

- PRD 尚未产出或仅完成第一阶段 → 先把 PRD 写完再来
- 技术方案评审、API / 数据库设计 review、UI 走查 → 超出 PRD 范围
- 需求还在 `prd-thinking` 阶段（背景未对齐）→ 错配 skill
- 用户要"表扬"或"整体打分" → 本 skill 只挑刺，不做整体评价
- 信息严重不足，无法判断真伪 → 直接说"无法判断 + 缺什么"，不要硬给结论

## 审核清单（7 项必查）

按以下顺序逐项过一遍，每一项都要给出"通过 / 有问题 + 具体位置"：

1. **未确认数据**：有没有把"待确认"的数字、概率、阈值当成确定数据写入？
2. **越权细节**：有没有写技术实现（接口、库、表结构）或设计参数（字号、颜色、布局）？
3. **范围边界**：本期"不做什么"是否写清楚？有没有偷偷塞进来的需求？
4. **异常与空态**：断网、无数据、权限不足、超时、并发、空列表、加载失败等是否漏掉？
5. **多余功能**：有没有"可有可无、不砍掉也没人用"的功能？
6. **问题 vs 方案**：是否在写"用户的问题"，还是只在写"用户想要的方案"？（方案错了，需求全错）
7. **验收用例**：是否有面向业务流程的验收 / 覆盖用例？是否覆盖了上下游依赖流程？

## 输出结构

按优先级分级输出问题，每条都包含：**位置 + 问题描述 + 改法**：

| 等级 | 含义 | 处理方式 |
|------|------|----------|
| **P0** | 必须改，否则开发会卡住或上线会爆 | 阻塞，必须修订后才能进入下一步 |
| **P1** | 强烈建议改，会显著降低后续返工成本 | 评审中讨论是否修订 |
| **P2** | 可选优化，让 PRD 更严谨 | 作者自行决定是否采纳 |

## 不做什么

- 不重写 PRD，只挑问题
- 不给夸奖、不维护面子（"整体不错"不算反馈）
- 不在没有上下文时强行给建议——信息不足时说"不知道"，读完再开口
- 不替作者拍板"砍不砍功能"——只指出风险和影响，但可以建议砍或重写
