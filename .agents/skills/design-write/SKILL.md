# Design Write — 两阶段技术设计

架构错了再补细节是白费。先锁架构、用户确认了再往下补。

## 边界 / 不适用场景

- PRD 尚未评审通过 → 先完成 PRD 评审
- 纯前端页面开发、样式调整 → 不需要技术设计文档
- 小修小补（改个字段、调个配置）→ 不需要完整设计文档
- 用户要求"直接写代码" → 先确认设计再动手

## 核心规则

- **必须基于 PRD**：设计文档的每个功能点都能追溯到 PRD 需求
- **不重复 PRD 内容**：背景、目标、用户场景不抄 PRD，直接引用
- **技术决策必须有理由**：选型、方案取舍要写清楚"为什么选 A 不选 B"
- **接口设计面向调用方**：REST API 要写清路径、方法、参数、响应、错误码
- **表结构要可直接建表**：字段名、类型、约束、索引都要明确
- **考虑已有架构约束**：复用项目已有的模块、组件、中间件，不重复造轮子
- **遵循项目规范**：接口设计参考 `dev-guide/后端规范.md`，数据模型参考 `dev-guide/数据库规范.md`

## 两阶段

### 第一阶段：锁架构与核心设计（用于锁方案）

只输出以下章节，得到用户确认后再进入第二阶段：

1. **元信息**（作者、版本、状态、关联 PRD）
2. **设计概述**（一段话说清楚整体方案，配一张架构图）
3. **技术选型**（新增的依赖/中间件/库，以及选型理由）
4. **核心模块设计**（按职责拆分的模块，每个模块的职责、对外接口、依赖关系）
5. **核心流程时序**（用 Mermaid 时序图描述关键业务流程的调用链）
6. **关键设计决策**（有争议或需要确认的技术点，列出备选方案及取舍理由）

### 第二阶段：补全细节（在架构确认后）

7. **接口设计**（REST API 详细定义：路径、方法、请求参数、响应结构、错误码）
8. **数据模型设计**（数据库表结构：字段、类型、约束、索引、ER 图）
9. **存储设计**（文件存储路径规则、OSS/MinIO 的 bucket/key 规范）
10. **异常处理设计**（对应 PRD 中每个异常场景的技术处理方式）
11. **安全设计**（鉴权方式、数据脱敏、接口防护）
12. **性能设计**（缓存策略、批量处理、超时控制、并发控制）
13. **日志与监控**（关键日志点、告警规则）
14. **部署与配置**（新增的配置项、环境变量、部署注意事项）
15. **待确认问题**（尚未闭环的技术开放项）

## 技术栈约束（JeecgBoot 项目）

设计时应优先考虑复用以下已有能力：

| 层次 | 技术 |
|------|------|
| 框架 | Spring Boot 3.x、MyBatis-Plus |
| 数据库 | MySQL / PostgreSQL |
| 缓存 | Redis |
| 文件存储 | OSS / MinIO（复用已有 jeecg-boot-starter-oss） |
| 接口文档 | Knife4j（Swagger） |
| 权限 | Spring Security + JWT |
| 工具 | Hutool、Lombok |

## 输出规范

- 架构图、时序图、ER 图统一使用 **Mermaid** 语法
- 接口示例使用 JSON 格式
- 表结构使用 Markdown 表格
- 文件输出到 `spec/{feature-name}/design.md`

## 工作流

1. 阅读关联的 PRD，理解需求范围
2. 进入第一阶段 → 输出架构与核心设计 → **停下来等用户确认**
3. 用户确认后 → 进入第二阶段 → 输出全部章节
4. 如有阻塞项 → 标注为"待确认"，不阻塞其他章节
