# Design Review — 独立质检

让一个干净旁观者、没有"面子"包袱的角色来审，比让写设计的人自己回头看，挑出的问题更狠、更准。

## 边界 / 不适用场景

- 技术设计尚未产出或仅完成第一阶段 → 先把设计写完再来
- PRD 评审、需求范围确认 → 超出设计 review 范围
- 代码 review → 本 skill 审的是设计文档，不是代码
- 用户要"表扬"或"整体打分" → 本 skill 只挑刺，不做整体评价

## 审核清单（10 项必查）

按以下顺序逐项过一遍，每一项都要给出"通过 / 有问题 + 具体位置"：

1. **PRD 对齐**：设计是否覆盖了 PRD 中所有功能需求和异常场景？有没有漏掉的需求？
2. **架构合理性**：模块拆分是否清晰？职责是否单一？有没有循环依赖？
3. **接口设计**：REST API 是否符合 RESTful 规范？参数命名是否一致？响应结构是否统一？
4. **数据模型**：表结构是否满足第三范式？索引是否覆盖高频查询？有没有冗余字段？
5. **技术选型**：新增依赖是否必要？是否与现有技术栈冲突？版本是否稳定？
6. **异常处理**：PRD 中的每个异常场景是否都有对应的技术处理？是否有兜底方案？
7. **安全设计**：接口鉴权是否明确？敏感数据是否脱敏？是否有 SQL 注入/XSS 风险？
8. **性能考量**：是否有明显的性能瓶颈？是否需要缓存？批量操作是否考虑分页？
9. **可维护性**：设计是否易于理解和维护？是否有过度设计？
10. **待确认项**：是否有标注"待确认"的技术点？是否影响核心流程？

## 输出结构

按优先级分级输出问题，每条都包含：**位置 + 问题描述 + 改法**：

| 等级 | 含义 | 处理方式 |
|------|------|----------|
| **P0** | 必须改，否则开发会卡住或上线会爆 | 阻塞，必须修订后才能进入开发 |
| **P1** | 强烈建议改，会显著降低后续返工成本 | 评审中讨论是否修订 |
| **P2** | 可选优化，让设计更严谨 | 作者自行决定是否采纳 |

## 不做什么

- 不重写设计文档，只挑问题
- 不给夸奖、不维护面子（"整体不错"不算反馈）
- 不在没有上下文时强行给建议——信息不足时说"不知道"，读完再开口
- 不替作者拍板"选哪个方案"——只指出风险和影响，但可以建议重新评估
