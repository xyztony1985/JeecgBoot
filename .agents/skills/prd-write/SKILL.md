# PRD Write — 两阶段写作

主体错了再补细节是白费。先锁范围、用户确认了再往下补。

## 边界 / 不适用场景

- 背景、范围、关键决策尚未对齐 → 先回 `prd-thinking` 拿到可写判定
- 用户要写技术方案、API 文档、数据库表结构、UI 走查 → 错配 skill
- 用户要求"一次性输出完整 PRD" → 仍应分两阶段，第一阶段必须停下来等用户确认
- 探索性、实验性需求尚未验证 → 先做 Demo / Spike，确认值得做再写
- 改动属于小修小补（文案、单个字段、局部体验）→ 不需要长 PRD

## 核心规则

- **不写**技术实现（接口、库、中间件、算法、数据库表结构等）
- **不写**设计参数（字号、颜色、间距、布局细节等）
- **不写**代码内容（伪代码、SQL、API 示例等）
- **不写**空话（"提升用户体验"、"打造极致产品"等无信息量表述）
- 数据必标来源：所有数字、阈值、概率、转化率必须标"待确认"或注明来源

## 两阶段

### 第一阶段：只写主体（用于锁范围）

只输出以下章节，得到用户确认后再进入第二阶段：

1. **元信息**（作者、版本、状态、关联文档）
2. **背景与目标**（为什么做、做成什么样算成功）
3. **用户范围**（目标用户、典型场景）
4. **本期范围和不做什么**（必须显式列出"不做什么"）
5. **核心流程**（主流程的端到端步骤）
6. **功能需求**（按功能点列出，每条都可独立验收）

### 第二阶段：补全细节（在主体确认后）

7. **异常情况与空态**（断网、无数据、权限不足、超时等）
8. **数据与隐私约束**（数据来源、留存期、敏感字段、权限）
9. **验收标准**（可量化的成功标准）
10. **面向业务流程的验收 / 覆盖用例**（覆盖主流程的端到端用例）
11. **上下游依赖**（依赖谁、被谁依赖、接入方式）
12. **待确认问题**（尚未闭环的开放项）

> 验收 / 覆盖用例**只验证业务主流程**，不写接口、数据库、缓存、算法实现。

## 工作流

1. 进入第一阶段 → 输出主体 → **停下来等用户确认**
2. 用户确认后 → 进入第二阶段 → 输出全部章节
3. 如有阻塞项 → 转回 `prd-thinking` 重新对齐
