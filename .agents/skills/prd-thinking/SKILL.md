# PRD Thinking — 写前背景与决策对齐

在动笔写 PRD 之前，先把"背景—边界—决策"三件事对齐，避免一开始就陷入正文细节。

## 边界 / 不适用场景

- 需求、范围、关键决策已经清晰对齐 → 转 `prd-write`
- 用户要先做 Demo / Spike 验证问题是否值得做 → 不是写 PRD
- 用户要技术方案、API 文档、UI 设计、代码 review → 错配 skill
- 改动很小且范围明确（例如文案调整、单个字段）→ 不需要长 PRD
- 用户要求"先出一版 PRD 看看" → 拒绝硬写，先做本 skill 拿到可写判定

## 必做步骤

1. 如果存在 `context/`，读取其中文件，理解产品现状、能力边界、已有约束
2. 如果存在 `inputs/`，读取其中文件，理解本次需求来源、原始诉求、提出方
3. **不输出 PRD 正文**，只输出对齐结果

## 输出结构

按以下 4 个模块组织输出：

| 模块 | 作用 |
|------|------|
| **背景理解卡** | 用一段话 + 关键事实列表，说清"现在是什么状态、为什么现在要做" |
| **背景诘问** | 列出对背景的疑问、潜在风险、待澄清的事实（开放问题清单） |
| **关键决策账本** | 把所有需要拍板的决策摆上桌：选项、影响、未决程度、建议 |
| **可写状态判断** | 明确给出"可写 / 不可写"的判定与剩余阻塞项 |

## 关键原则

- **关键决策账本是核心**：先把要拍板的决策摆上桌，不要在正文里绕。
- 只有当背景、上下游、关键决策、范围、阻塞问题都处理清楚后，才进入 `prd-write`。
- 如果任一项未对齐，输出"不可写 + 阻塞清单"，不要硬写。

## 不做什么

- 不写 PRD 正文（标题、章节、流程图等都不写）
- 不预设技术方案、不预设交互细节
- 不假装对齐——遇到不确定项必须标记为"待确认"
